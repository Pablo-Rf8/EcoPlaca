Objetivos y requisitos

EcoPlaca gestiona hardware en desuso para facilitar recuperación, reutilización y trazabilidad. Su vínculo con ODS 11 y 12 se basa en la gestión de residuos y el uso responsable de recursos.

04 · Seguridad

Autenticación y autorización

01CredencialesLogin
02BCryptHash
03JWTToken
04MiddlewareFirma + rol

Contrato

  • Registro acepta rolId 2/3; no permite ADMIN público.
  • Login compara BCrypt y devuelve data.token y data.usuario.
  • Perfil recupera datos activos; Angular normaliza sus campos.
  • JWT_EXPIRES_IN acepta segundos o s/m/h/d/w; ejemplo 7d.
  • authorizeRoles consulta el rol y actividad actuales en MySQL.

Sesión y guards

AuthService expone currentUser e isAuthenticated con Signals, guarda JWT en localStorage, restaura con el perfil y limpia estado en logout/expiración. Los eventos de almacenamiento sincronizan cambios entre pestañas.

authGuard redirige a /login con returnUrl. roleGuard aplica data.roles y vuelve al Catálogo con aviso si faltan permisos. El interceptor añade JWT solo a la API configurada, excluyendo login y registro.

Límite de localStorage

Es accesible a JavaScript y no ofrece protección HttpOnly. Los guards no sustituyen la autorización del servidor. No hay refresh tokens ni recuperación de contraseña en pantalla.

Entorno

DB_HOST, DB_USER, DB_PASSWORD y DB_NAME son obligatorios. JWT_SECRET es obligatorio y requiere al menos 32 caracteres en producción. CORS acepta orígenes explícitos; no autoriza operaciones por rol.

05 · Reserva / entrega

Proceso transaccional

Solicitar transferencia

  1. Validar dispositivo, motivo y destino opcional; obtener conexión.
  2. Iniciar beginTransaction y bloquear dispositivo con FOR UPDATE.
  3. Exigir DISPONIBLE, ausencia de orden activa y centro de origen.
  4. Validar centros activos y compatibles con la categoría.
  5. Crear orden PENDIENTE y cambiar dispositivo a RESERVADO.
  6. Commit; rollback ante error; liberar conexión en finally.

Completar transferencia

  1. Validar ID y localizar dispositivo de la orden.
  2. Bloquear primero dispositivo y luego orden para conservar el orden de bloqueo.
  3. Exigir técnico responsable o ADMIN, orden PENDIENTE/EN_TRANSITO y dispositivo RESERVADO.
  4. Cambiar a COMPLETADA con fecha_completado y dispositivo ENTREGADO.
  5. Aplicar centro destino cuando corresponde y hacer commit.
  6. Repetición o estado incompatible: 409 sin duplicar el impacto.
Concurrencia

Los bloqueos impiden dos reservas simultáneas exitosas del mismo hardware. Los errores concurrentes revierten la transacción y permiten informar el conflicto.

Métricas

La consulta agrega peso y CO₂ de dispositivos recuperados una vez, sin multiplicarlos por órdenes históricas. Los conteos de transferencias por estado se obtienen mediante la misma sentencia SQL.

Reactividad

Signals guardan sesión, resultados, selección y estados visuales. Reactive Forms valida formularios. El catálogo combina filtros, aplica debounce de 350 ms y switchMap cancela consultas anteriores.

Mutaciones

TransferenciasService emite cambios$ después del éxito. La vista actualiza COMPLETADA/ENTREGADO y retira la orden activa. El Dashboard consulta al abrirse y reacciona al evento si está montado; otros clientes se reflejan en la próxima consulta.

Accesibilidad y diseño

Paleta #1B4965 y #2EC4B6. Navegación responsiva y por teclado, formularios etiquetados, errores visuales y diálogos nativos que protegen envíos en curso.

Persistencia

Las notas del dispositivo pertenecen a MySQL. La pantalla Comentarios y notas usa demostración/estado local y avisa que lo añadido se pierde al salir o recargar.

Método / rutaAccesoFunción
POST /transferenciasTECHNICIANReserva.

Solicitud — ejemplo

{
  "dispositivoId": 123,
  "motivo": "Reacondicionamiento para reutilización",
  "centroDestinoId": 2
}

centroDestinoId es opcional y, si se envía, debe ser compatible. mis-ordenes no deja seleccionar las órdenes de otro técnico mediante parámetros.

Métricas — ejemplo ilustrativo

{
  "success": true,
  "data": {
    "totalKgRecuperados": 1.25,
    "co2EvitadoKg": 44.38,
    "transferenciasPorEstado": {
      "PENDIENTE": 1,
      "EN_TRANSITO": 0,
      "RECIBIDO": 0,
      "CANCELADO": 0,
      "COMPLETADA": 1
    }
  }
}

Se suma peso_kg y co2_evitado_kg de estados ENTREGADO/RECICLADO. El cálculo de cada dispositivo usa la utilidad ambiental y el factor de categoría.

Conteos

La API conserva RECIBIDO/CANCELADO históricos. Angular suma PENDIENTE + EN_TRANSITO + COMPLETADA en su tarjeta de transferencias.

Errores habituales

400: datos; 401: sesión; 403: rol/propiedad; 404: entidad; 409: estado, vínculos, duplicación o concurrencia.

Entorno, migración y seed

VariableUso
DB_HOST / DB_PORTServidor MySQL y puerto.
DB_USER / PASSWORD / NAMECredenciales privadas y base obligatorias.
JWT_SECRETFirma; ≥32 caracteres en producción.
JWT_EXPIRES_INSegundos o sufijo s/m/h/d/w; ejemplo 7d.
CORS_ORIGINSOrígenes exactos, separados por comas; HTTPS en producción.
SEED_ADMIN_EMAIL / PASSWORDADMIN opcional; contraseña ≥12 caracteres y ≤72 bytes.
SEED_ADMIN_NOMBRENombre del administrador.
SEED_CENTRO_NOMBRE / DIRECCION / CIUDADCompletar los tres para crear centro inicial real.

Migración

db:migrate ejecuta dist/scripts/migrate.js. 001 crea las siete tablas con CREATE TABLE IF NOT EXISTS. 002 añade ENTREGADO/COMPLETADA si faltan en los ENUM. Se verifica information_schema y se usa GET_LOCK para evitar preparación simultánea.

Seed

Crea roles y categorías faltantes; ADMIN opcional solo si no existe. No promueve cuentas ni restablece contraseñas. DONOR/TECHNICIAN se registran por API. El centro inicial existente conserva su configuración.

Protección de datos

DB/ecoplaca_DB.sql contiene DROP DATABASE. No usarlo con datos que deban conservarse. El despliegue usa DB/migrations, no reinicializa la base.

DDL

MySQL puede hacer commit implícito en cambios de esquema. Las migraciones verifican estado y son repetibles; no prometen rollback total del DDL. El seed sí agrupa cambios de datos en transacción.

13 · Despliegue

Producción y operación

1. Configurar y compilar

Crear base y credenciales. Definir NODE_ENV=production, JWT_SECRET, JWT_EXPIRES_IN y CORS_ORIGINS con dominio HTTPS real. Instalar dependencias de desarrollo durante la construcción.

npm ci
npm run build

2. Preparar base y arrancar

Desde backend/:

npm run deploy

Encadena db:prepare y npm start. Una preparación fallida impide arrancar. Puede ejecutarse db:prepare como etapa separada y npm start como proceso de servicio.

3. Publicar Angular

  • Servir frontend/dist/frontend/browser con HTTPS.
  • Reescribir rutas Angular a index.html para acceso directo.
  • Enviar /api al backend conservando el prefijo y antes del fallback Angular.
  • Conservar backend/dist, dependencias de producción y DB/migrations con posición relativa del repositorio.

4. API en otro origen

Proporcionar API_URL en frontend/src/app/app.config.ts, recompilar y permitir el origen del frontend en CORS_ORIGINS. proxy.conf.json solo configura desarrollo.

5. Operación

Comprobar salud, login y el ciclo completo con cuentas autorizadas. El servidor valida entorno y conectividad antes de escuchar y maneja SIGTERM/SIGINT para cerrar HTTP/pool. Añadir respaldo y monitoreo según la instalación.

Secretos

No usar contraseñas demo en producción. Este documento no incluye ni modifica el .env real.

Límites y mantenimiento

Alcance actual

  • Sin WebSockets/SSE: cambios de otros clientes llegan en la próxima consulta.
  • CRUD de categorías/centros y edición/retiro de hardware por API, sin pantallas.
  • Sin recuperación de contraseña, refresh tokens, chat ni agenda.
  • Comentarios y notas de taller es local; no persiste en MySQL.
  • CO₂ es una estimación configurable, no una certificación.

Mantenimiento

  1. Revisar contratos y formatos antes de añadir campos o endpoints.
  2. Mantener SQL parametrizado, validación y autorización por rol/propiedad.
  3. Proteger historial y probar concurrencia y conflictos.
  4. Actualizar README, entorno de ejemplo y documentación si cambia el comportamiento.
  5. Ejecutar pruebas y validar en QA antes de producción.
